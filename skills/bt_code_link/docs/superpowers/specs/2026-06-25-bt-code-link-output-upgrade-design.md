# bt_code_link 输出协议设计

## 问题定义

`bt_code_link` 的输出必须是**重协议、中文主导、结构化强**的分析文档，而不是简版摘要。

当前需要解决以下问题：

1. 避免输出退化成"简版报告"（只有函数列表 + 结论）
2. 中文为主导，函数/类/接口名保留英文
3. 章节协议必须稳定，不同链路保持统一文风
4. 必须对层级路径合理性做显式判断，而不是只追函数

## 设计目标

1. 最终输出的 Markdown 文档以**中文章节说明、中文分析文字、中文结论**为主
2. 函数名、类名、接口名、宏名、调用链节点名保持源码英文
3. 默认输出必须包含重型结构章节，不允许只有简版分析
4. 支持根据目标链路自动切换不同输出骨架，同时保持统一文风
5. 保留 prompt-first skill 形态，不引入重脚本依赖

## 非目标

1. 本次不把 skill 改造成独立代码解析器
2. 本次不要求自动生成完全准确的调用图数据库
3. 本次不强制覆盖所有 BT 子场景，只先完善主流链路分析协议

## 设计结论

采用 **重协议型 prompt-first skill**。

这意味着：

1. 不新增复杂执行脚本作为主能力
2. 把主要提升放在 `SKILL.md` 的输出协议、章节约束、分层规则、质量门槛上
3. 用多个参考文件把"参考文档风格"固化成可重复执行的交付标准

## 升级后的文件结构

`bt_code_link` 包含以下结构：

1. `SKILL.md`
   - 中文主导
   - 明确最终文档必须为中文主导输出
   - 明确不同链路的章节协议
   - 明确质量门槛与失败条件
2. `references/layer-map.md`
   - BT 分层说明与按需错误订正规则
   - 规定何时需要输出订正、何时只输出说明
3. `references/report-template.md`
   - 重型中文模板
   - 默认包含所有必须章节
4. `references/target-protocols.md`
   - 定义不同目标链路的专属输出协议
   - `bt_enable`、`bt_connect`、`bt_scan`
5. `README.md`
   - 中文使用说明

## 输出协议：默认章节顺序

最终文档默认章节顺序为：

1. `# 概览`
   - 分析对象、源码路径、目标链路、结论先行
2. `# 层级路径说明`
   - 说明本次分析涉及的层级划分
   - 解释 Framework / BT Module / Stack / HAL / Controller 的边界
3. `# 层级错误订正`
   - **按需输出**
   - 仅当用户提供的层级、路径或职责归属有问题时输出
4. `# 完整调用链`
   - 以树形或分层链路形式输出完整主链
5. `# 关键函数分层解析`
   - 每层给出入口、关键决策点、下一跳、函数意义
6. `# Mermaid 时序图`
   - 至少一张跨层时序图
7. `# Mermaid 分阶段流程图`
   - 至少两张，按执行阶段拆分
8. `# 代码状态机图`
   - 仅限真实代码 StateMachine
9. `# 架构说明`
   - 分析各层职责、边界、通信方式
10. `# 关键源码索引`
    - 以表格输出关键文件、用途、层级归属
11. `# 变体、风险点与未解析边界`
    - 标注 vendor 差异、推断点、源码断点

## 中文化规则

1. **章节标题必须中文**
2. **解释文字、分析文字、结论必须中文**
3. **函数名、类名、接口名、宏名、调用链节点名保持英文**
4. **图中注释优先中文，但源码符号维持英文**

## 链路自适应协议

### `bt_enable`

重点输出：

- Settings → BluetoothAdapter → AdapterService → AdapterStateMachine
- BTIF / BT Stack 初始化链路
- HAL 初始化边界
- BT Enable 状态机
- BT Enable 相关文件索引

### `bt_connect`

重点输出：

- `CachedBluetoothDevice` → Profile Service → Profile StateMachine
- BTIF / BTA Profile 连接执行链路
- 连接状态机（`A2dpStateMachine` / `HeadsetStateMachine`）
- Profile 相关文件索引

### `bt_scan`

重点输出：

- `BluetoothAdapter.startDiscovery()` / `BluetoothLeScanner.startScan()`
- `AdapterService.startDiscovery()`
- BTIF / BTA 扫描执行链路
- 扫描相关文件索引

### 自适应通用规则

1. 大章节顺序保持统一
2. 子章节内容按目标链路替换
3. 如果用户描述模糊，skill 先判断更接近哪一类链路，再套用对应协议

## 层级说明与按需订正规则

1. 先检查用户给出的层级路径、模块归属和职责关系
2. 如果层级与路径合理，只输出"层级路径说明"
3. 如果发现如下问题，则增加"层级错误订正"：
   - 路径错误
   - BT Stack 被误当作 HAL
   - BT Service APK 与 BT Framework Module 混为一谈
   - HAL 接口定义与 vendor HAL 实现混淆
4. 订正内容必须包含：
   - 错误点
   - 正确归属
   - 修正后的层级结构图或文字结构

## 强制质量门槛

1. 没有"层级说明、完整调用链、时序图、分阶段流程图、关键源码索引"就不能算完成
2. 不能只给结论，必须给到源码证据
3. 到 HAL / Stack / Controller 的每个边界都要标注：
   - 已证实
   - 间接推断
   - 未解析
4. 至少一张时序图 + 至少两张分阶段流程图
5. 文件索引章节为强制项
6. 输出语言必须满足"中文说明 + 英文符号"的约束

## 错误处理策略

1. 如果找不到目标路径，必须明确说明"源码缺失"而不是跳过
2. 如果 lower-layer 只能追到 BT Stack，必须说明断点位置
3. 如果用户的层级输入本身没有问题，不要强行写"错误订正"
4. 如果目标链路不匹配当前协议，要在概览中说明采用了哪个最接近的协议

## 验收标准

1. 文档默认以中文说明为主
2. 对同类问题的输出章节更稳定
3. 能看出"层级说明、时序图、分阶段流程图、架构说明、文件索引"已固化为协议
4. 不再容易退化成简版函数链列表

## 已确认决策

1. 输出协议采用重结构化方案
2. 最终文档默认强制输出重型章节
3. 输出总体中文为主，但函数链路与源码符号保留英文
4. `层级错误订正` 改为按需输出，不是每次强制出现
5. skill 要支持按目标链路自动切换章节骨架
