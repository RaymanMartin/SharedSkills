# wifi_code_link 输出协议升级设计

## 问题定义

当前 `wifi_code_link` 已经能完成基础链路追踪，但输出仍偏“轻报告”：

1. 章节过少，只有概要、函数表、时序图、状态机等基础块。
2. 结果偏英文风格，不符合当前使用场景对中文技术文档的要求。
3. 没有对“层级路径是否合理”进行显式解释，也缺少参考文档中的架构说明、文件索引、分层职责解释。
4. 输出协议没有针对不同链路目标（如 `sap_open`、`sta_init`、`wifi_toggle`）做强约束的章节切换。

用户希望把它升级成**重协议、中文主导、结构化更强**的 skill，并尽量对齐参考文档：

`/home/quectel/Work/CopilotDoc/wifi_init_chain_analysis.md`

## 升级目标

1. 最终输出的 Markdown 文档以**中文章节说明、中文分析文字、中文结论**为主。
2. 函数名、类名、接口名、宏名、调用链节点名保持源码英文。
3. 默认输出必须包含重型结构章节，而不是只有简版分析。
4. 支持根据目标链路自动切换不同输出骨架，同时保持统一文风。
5. 保留 prompt-first skill 形态，不引入重脚本依赖。

## 非目标

1. 本次不把 skill 改造成独立代码解析器。
2. 本次不要求自动生成完全准确的调用图数据库。
3. 本次不强制覆盖所有 Wi-Fi 子场景，只先完善主流链路分析协议。

## 设计结论

采用 **重协议型 prompt-first skill**。

这意味着：

1. 不新增复杂执行脚本作为主能力。
2. 把主要提升放在 `SKILL.md` 的输出协议、章节约束、分层规则、质量门槛上。
3. 用多个参考文件把“参考文档风格”固化成可重复执行的交付标准。

## 方案比较

### 方案 A：轻度模板升级

只把原有模板翻译为中文，并增加少量章节。

**优点**
- 改动最小
- 风险低

**缺点**
- 仍然容易输出成“简版报告”
- 很难稳定对齐参考文档风格

### 方案 B：增强协议型 skill

保留当前结构，但强化章节、图表和证据要求。

**优点**
- 成本适中
- 比现状稳定很多

**缺点**
- 对“层级纠错、架构说明、索引”这类重型内容约束仍不够强

### 方案 C：重结构化协议升级（本次选择）

在 prompt-first 基础上，引入更强的章节协议、链路类型协议、文件索引协议和分层纠错协议。

**优点**
- 最接近参考文档风格
- 输出一致性最高
- 更适合系统级链路分析沉淀

**缺点**
- `SKILL.md` 和 reference 文件会明显变大
- 使用时的质量约束更重

## 输出协议升级

升级后，最终文档默认章节顺序为：

1. `# 概览`
   - 分析对象
   - 源码路径
   - 目标链路
   - 结论先行
2. `# 层级路径说明`
   - 说明本次分析涉及的层级划分
   - 解释 framework / daemon / HAL / kernel / driver 的边界
3. `# 层级错误订正`
   - **按需输出**
   - 仅当用户提供的层级、路径或职责归属有问题时输出
4. `# 完整调用链`
   - 以树形或分层链路形式输出完整主链
5. `# 关键函数分层解析`
   - 每层给出入口、关键决策点、下一跳、函数意义
6. `# Mermaid 流程图`
   - 至少一张主流程图
   - 复杂链路可以拆成多张图
7. `# 状态机图`
   - 针对目标链路输出状态机
8. `# 架构说明`
   - 分析各层职责、边界、通信方式
9. `# 关键源码索引`
   - 以表格输出关键文件、用途、层级归属
10. `# 变体、风险点与未解析边界`
   - 标注 vendor 差异、推断点、源码断点

## 中文化规则

升级后的语言规则如下：

1. **章节标题必须中文**
2. **解释文字、分析文字、结论必须中文**
3. **函数名、类名、接口名、宏名、调用链节点名保持英文**
4. **图中注释优先中文，但源码符号维持英文**

这条规则适用于 `SKILL.md` 的输出要求，也适用于模板示例。

## 链路自适应协议

为了让 skill 不只服务 SAP，一套统一风格协议下，按目标链路切换重点：

### 1. `sap_open`

重点输出：

- Settings / Tethering / SoftAp 主链
- Hostapd 相关路径
- AP 启动流程图
- SAP 状态机
- 热点相关文件索引

### 2. `sta_init`

重点输出：

- `setWifiEnabled` 到连接流程
- ClientMode / Supplicant 主链
- STA 初始化流程图
- STA 连接或 WiFi 启动状态机
- STA 相关文件索引

### 3. `wifi_toggle`

重点输出：

- Wi-Fi 开关切换
- `ActiveModeWarden` / 状态机仲裁
- 开关状态机
- 模式管理文件索引

### 自适应通用规则

1. 大章节顺序保持统一。
2. 子章节内容按目标链路替换。
3. 如果用户描述模糊，skill 先判断更接近哪一类链路，再套用对应协议。

## 层级说明与按需订正规则

升级后的 `layer-map.md` 需要执行以下规则：

1. 先检查用户给出的层级路径、模块归属和职责关系。
2. 如果层级与路径合理，只输出“层级路径说明”。
3. 如果发现如下问题，则增加“层级错误订正”：
   - 路径错误
   - daemon 被误当作 HAL
   - vendor HAL / hostapd / driver 边界混淆
   - framework 与 module 分层归属错误
4. 订正内容必须包含：
   - 错误点
   - 正确归属
   - 修正后的层级结构图或文字结构

## 强制质量门槛

升级后，skill 必须满足以下完成条件：

1. 没有“层级说明、完整调用链、流程图、关键源码索引”就不能算完成。
2. 不能只给结论，必须给到源码证据。
3. 到 HAL / hostapd / kernel / driver 的每个边界都要标注：
   - 已证实
   - 间接推断
   - 未解析
4. 至少一张主流程图 + 一张状态机图。
5. 文件索引章节为强制项。
6. 输出语言必须满足“中文说明 + 英文符号”的约束。

## 错误处理策略

1. 如果找不到目标路径，必须明确说明“源码缺失”而不是跳过。
2. 如果 lower-layer 只能追到 daemon 或 HAL，必须说明断点位置。
3. 如果用户的层级输入本身没有问题，不要强行写“错误订正”。
4. 如果目标链路不匹配当前协议，要在概览中说明采用了哪个最接近的协议。
